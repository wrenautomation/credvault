# Brief: API keys as credentials (credvault 0.13.0)

Bead wa-sos.1. Design: `autobrowse/designs/2026-10-19-api-keys-as-accounts.md` (read "Target" and "Order" first). This brief is the credvault part only: a library. The CLI (`creds key ...`) and the migration command live in autobrowse (the next brief); credvault gives them the pieces.

## Build

New module `src/keys.ts`, its test `src/keys.test.ts`, exports in `src/index.ts`, a README row per new piece, version 0.13.0 in `package.json`. Add optional fields to `SecretUse` in `src/audit.ts`. Nothing else changes; logins (`credentials.ts`) stay as they are.

### 1. The key

`apiKeySchema` (zod), types `ApiKey` and `ApiKeyInput`:

| field | rule |
|---|---|
| `site` | the vendor: `/^[a-z][a-z0-9-]{0,39}$/` (`anthropic`, `exa`, `google-maps`) |
| `account` | the label: `/^[a-z0-9][a-z0-9.-]{0,63}$/` (`autobrowse-prod`, `env-0`) |
| `owner` | `wren` (the operator) or an owner name (`OWNER_NAME` from `owner.ts`) |
| `secret` | the key, non-empty, trimmed |
| `via` | optional: the login it was minted from (`anthropic@william`) |
| `vendorId` | optional: the vendor's own name or id for the key (the Console key name) |
| `purposes` | `ROLE_NAME` words, default `[]`. `default` is the purpose the bare env name projects from |
| `status` | `live` \| `spent` \| `revoked`, default `live` |
| `spentUntil` | ISO datetime, only with `spent` (refine) |
| `madeAt` | ISO datetime, required |
| `revokedAt` | ISO datetime, only with `revoked` |
| `cap` | optional `{ amount: positive number, unit: "calls" \| "micros" }`: a monthly cap |
| `previous` | ids of keys this one replaced: `[{ id, vendorId?, revokedAt }]`, default `[]`. Never a secret |

No `lastUsedAt` or `uses` field: they come from the audit (see 5). A write per use would be an SSM write per API call.

Helpers:
- `keyId(secret)`: sha256 hex, first 12 chars. The same as autobrowse `key-ring.ts` `fingerprint` (autobrowse will import this one).
- `keyAddress(site, account)` → `site@account`; `parseKeyAddress(address)` → `{site, account}` or throws with the rule it broke.
- `KeyInfo` = `Omit<ApiKey, "secret"> & { address: string; id: string }`; `keyInfo(key)` makes one. Every listing returns `KeyInfo`, never a secret.
- `liveAt(key, now)`: `live`, or `spent` with `spentUntil` <= now.

### 2. The store

```ts
interface KeyStore {
  get(address: string): Promise<ApiKey | null>;
  put(key: ApiKeyInput): Promise<ApiKey>;      // address from site + account
  list(): Promise<KeyInfo[]>;                  // every key, no secrets, sorted by address
  remove(address: string): Promise<boolean>;
}
```

- `envKeys(store: EnvStore): KeyStore`: one row per key, the row value is the key as JSON, the row name is `keyRowName(address)` = `envSiteName(address)` (`exa@env-1` → `EXA__ENV_1`; read back with `siteFromEnvName`). The caller points the `EnvStore` at its own place (autobrowse uses `ssmEnvStore(ssm, "<path>/keys")`, one level below the env names, so `env ls` and the box's deploy never see the rows). SSM keeps 100 versions of each row: that is the key's history. `list` uses `store.all()` (ssmEnvStore decrypts each version once per process).
- `memoryKeys(init?)` = `envKeys(memoryEnvStore(...))`, for tests and callers.
- `put` refuses (throws, no write) when another key of the same `site` and `owner` that is not `revoked` holds one of its purposes. The message names both addresses and says `creds key purpose <address> <purpose>` moves it. One key per purpose per vendor per owner.
- `movePurposes(store, address, purposes)`: gives `address` these purposes and takes them off any other key of the same site and owner, in one call. The caller's explicit move.

### 3. The ring

`keysFor(store, { owner, vendor, purpose?, now? }): Promise<ApiKey[]>`: keys with `site === vendor`, `owner === owner`, `liveAt(now)`. Order: the key holding `purpose` (when given), then the `default` key, then the rest by `madeAt`, ties by account in natural order (`env-2` before `env-10`). No duplicate ids (first wins).

`keysFor` is the only ring order. The projection below uses the same order.

### 4. The env projection

Env is a view of the vault, one way. Per vendor, from its keys that are not `revoked` (live and spent both: env readers have their own spent logic, and a spent key comes back on its date with nobody to re-project it):

- `<BASE>_API_KEY` = the `default` key, else the first in ring order. `BASE` = `site.toUpperCase()` with `-` → `_`.
- `<BASE>_API_KEY_1..n` = the rest, in ring order (purpose ignored), and `NUM_<BASE>` = `n`. With no rest, neither the numbered names nor `NUM_<BASE>` exist.

Functions (all pure or take an `EnvStore`; none prints or returns a value except `projectKeys`, whose result the caller writes):
- `vendorBase(site)`, and `parseVendorKeyName(name)` → `{ vendor, slot: number | null } | null` for `X_API_KEY` / `X_API_KEY_<n>` (vendor = `x` lowercased, `_` → `-`), plus `isProjectedName(name)` (also `NUM_<BASE>`).
- `projectKeys(keys: ApiKey[]): Map<vendor, EnvEntry[]>`.
- `applyProjection(store: EnvStore, keys: ApiKey[], o?: { vendors?: string[] })`: per vendor in `keys` (or `o.vendors`; a vendor named with no keys left clears its names): puts each name whose stored value differs (compare by `keyId`, never print), removes stale `<BASE>_API_KEY_k` (k > n) and a stale `NUM_<BASE>`. Returns `{ put: string[], removed: string[] }` (names only). Writes nothing for a name already equal: no SSM version churn.
- `projectionDiff(store: EnvStore, keys: ApiKey[], o?: { vendors?: string[] })`: what `applyProjection` would change, as `{ name, want: id | null, have: id | null }[]` (ids by `keyId`; `NUM_` rows compare the number). Empty = env equals the vault. This is the migration's proof.

### 5. Audit

`SecretUse` (`src/audit.ts`) gains optional `owner?: string`, `keyId?: string`, `reason?: string`. A key use is recorded as `{ credential: <address>, field: "secret", site: <vendor>, url: <endpoint without query>, by, owner, keyId, reason, allowed }`. Old lines (without the new fields) still verify: the chain hashes whatever the row holds, so check `verifyChain` over a mix in a test.

`keyUses(uses: SecretUse[])` → `Map<keyId, { uses: number; lastUsedAt: string }>`: the "last use" and count the CLI shows. Allowed uses only.

### 6. Migration piece

`keysFromEnv(entries: EnvEntry[], { owner, madeAt }): { keys: ApiKeyInput[]; skipped: { name, why }[] }`: every `<BASE>_API_KEY` and `<BASE>_API_KEY_<n>` becomes a key: the bare name → account `env-0` with purpose `default`; `_<n>` → account `env-<n>`; status `live`; one `madeAt` for all (the ring then orders the rest by account, which reproduces `_1..n`). `NUM_<BASE>` is read, not kept: a numbered name past `NUM_<BASE>` is skipped (`why: "past NUM_<BASE>"`), as today's rings never read it. Two names with the same value: kept once, at the lower slot, and the other is skipped (`why: "same key as <name>"`); the caller's `projectionDiff` then shows the name that would move, and the migration stops on it. Pure; values only pass through.

## Tests (synthetic keys only, e.g. `sk-test-aaaa…`)

- schema: refines (spentUntil only with spent), bad site/account rejected, address round trip including `.` and `-`.
- `envKeys` over `memoryEnvStore`: put/get/list/remove; list has no `secret` key anywhere (assert on `JSON.stringify`); purpose clash throws and writes nothing; `movePurposes` moves.
- `keysFor`: purpose first, then default, then madeAt, natural tie order; spent before/after `spentUntil`; revoked out; other owner out.
- projection: one key (bare only); three keys (bare + _1.._2 + NUM=2); default not first by madeAt; `applyProjection` removes stale `_3` and `NUM_` after a revoke; second apply writes nothing; `projectionDiff` empty after apply.
- `keysFromEnv` then `projectKeys` reproduces `X_API_KEY`, `X_API_KEY_1..2`, `NUM_X=2` exactly (the migration's round trip); duplicate value case; past-NUM case.
- audit: mixed old/new rows verify; `keyUses` counts.
